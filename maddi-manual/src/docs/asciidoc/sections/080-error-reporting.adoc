[[error-reporting]]
= Reading the output: errors, warnings, exit codes

A run reports what happened in two channels: a human-readable *summary* logged at the end, and a
*process exit code*.

== Errors versus warnings

{maddi} distinguishes two severities, because it analyzes with a partial classpath and must tolerate the
gaps:

*Warnings* are non-fatal. The most common is a reference to a type that is not on the classpath, which the parser
passes on from javac's diagnostics. Warnings do not stop the run and do not, on their own, make it fail. They
are listed in the summary with their file, line and column, capped to keep the output readable.

*Errors* are genuine failures: a syntax error, an IO failure setting up a source set, or an exception
during analysis. Errors are listed in the summary and drive the exit code.

== The summary

Unless `--quiet` (CLI) / `quiet = true` (Gradle) is set, the run prints, at the end, the collected
errors and warnings — each with its location and message. This is the first thing to read when a run
does not produce the results you expected.

== Exit codes

The exit code reflects the outcome; a parse error never yields `0`. The full table is in
<<appendix-exit-codes>>. In short:

* `0` — success;
* `2` — a parser/inspection error (a source failed to parse);
* `4` — an IO failure;
* `5` — an analyzer error (the modification analysis threw);
* `6` — the Java analyzer met Kotlin sources;
* `7` — an option was given that this pipeline cannot honour;
* `1` — an unexpected internal error.

The Gradle plugin turns any non-zero code into a task failure; the Maven plugin fails the build; the
CLI returns the code from `main` (a launcher will `System.exit` with it).

== Fail-fast versus accumulate

The parse can run in *fail-fast* mode (stop and report at the first error) or *accumulate* mode (collect
all errors, then report). The command line accumulates by default; a single syntax error still yields
a parser exit code, but you see every problem the parse found rather than only the first.

== Near misses, and why a verdict holds

`--warn-near-misses` (`warnNearMisses` in the plugins) adds advisory warnings for types and methods that narrowly
miss a property: a type that would be `@Container` but for one modifying parameter, for example.
For the reasons behind any single verdict — why a method is `@Modified`, where a type stops on the way to
`@Immutable` — ask the <<agents-and-ides,MCP server>> (`explain`) or look in an IDE plugin.
