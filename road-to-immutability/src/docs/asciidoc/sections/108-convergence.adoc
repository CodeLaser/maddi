[[convergence]]
= Convergence: the iterating analyzer

The previous chapter described how links are computed for one method, given the summaries of the methods
it calls.
This chapter describes the layer above: how the analyzer orders the work, iterates it to a fixpoint,
knows when it is done, and what it does when the code refuses to cooperate.
Like the previous chapter, it is technical in nature.
It describes the design of the iteration: what must hold for a result to be trusted, and why the work is organised
the way it is.
The particulars of the current engine (its classes, thread counts, switches and measurements) are in
<<analyzer-today-engine>>.

== Properties, and the discipline of writing them

Every conclusion the analyzer draws — a method is non-modifying, a field's content is unmodified, a type
is immutable at some level — is a _property value_ attached to a method, field or type.
Three rules govern them:

* Values are written at most once per analysis, and always in the _conservative-to-optimistic_ direction:
  an absent value means "not decided yet", never "assumed fine".
  A guarded overwrite facility exists for the few places that legitimately refine a
  value (cycle breaking, below), and it enforces monotonicity: a verdict may become more precise, never
  contradict itself.
  The one sanctioned exception is the modification cutover after the fixpoint (<<after-the-fixpoint>>).
* Undecided is a first-class state.
  An analyzer component that cannot conclude — because a field's type is not yet decided, a supertype is
  still open, a callee's summary is missing — returns "no value" and will simply be visited again.
* Decisions are local, dependencies are explicit.
  The immutability of a type depends on its fields' finality and modification status, its methods'
  modification status, and its supertypes' immutability; each of those is itself a property, computed by
  its own component.

== Ordering the work

Before iteration starts, the analyzer computes an _analysis order_ from the call graph and the type
hierarchy: methods before their callers where possible, subtypes and enclosing types grouped, fields
between their initializers and their readers.
Two prepared ingredients matter beyond ordering:

* _part of construction_: the set of methods only reachable from constructors.
  Assignments there do not count against a field's effective finality — the essence of the
  effectively-final rule of the chapter on <<finalfields>>.
  Note that assignments to a nested type's fields may come from the enclosing type, a sibling type, or a
  lambda anywhere in the primary type; the computation scans the whole primary type.
* _shallow summaries_ for everything outside the parsed source: JDK and library types receive their
  properties from the annotated APIs (below) or conservative defaults.

Java being Java, the call graph has cycles — recursion, mutual recursion, callbacks — so a single pass in
analysis order cannot suffice.
Hence: iteration.

== The iteration loop

The main loop repeatedly runs the per-element analyzers over the analysis
order, counting _property changes_ — the number of newly decided or refined values in the pass.
The first pass visits everything; subsequent passes narrow to a _worklist_: only elements whose inputs
changed in the previous pass are dirty and revisited, with dirty targets mapped to their enclosing
analysis-order element.

The loop can run in parallel: elements of the analysis order that do not depend on each other can be processed
at the same time.
The write-once discipline is what makes this possible, but it does not make the result independent of scheduling
by itself: a verdict that depends on whether a sibling was decided in the same pass or in the previous one can
come out differently.
Such shapes must be known, and must resolve to the conservative side.

== Verification and certification

Reaching "no more changes" is necessary but not sufficient: a fixpoint reached through optimistic
intermediate states could in principle rest on values that would not be re-derived from scratch.
The loop therefore ends with _verification passes_: with all values frozen, every element is recomputed
once more and the engine checks that nothing changes.
A run that exits this way is _certified_: the published verdicts are a self-consistent fixpoint of the
analysis functions, independent of the path that produced them.

== Cycle breaking

Some clusters never decide on their own.
The classic shape: type A's immutability waits on field type B, whose immutability waits on a method
whose modification verdict waits on A.
Everyone is undecided, nobody moves, and the loop reaches its certification point with a residue of
undecided types.

At exactly that point — quiescence, with undecided immutability remaining — the engine activates _cycle
breaking_: one more full pass in which the blocked components are allowed to resolve their undecided
inputs by strategy rather than waiting.
The default strategy floors an undecided supertype at final-fields level and treats absent information as
non-modifying; the breaking pass then lets the normal machinery draw its conclusions, and the loop
re-certifies including them.
Without it, a code base with many such clusters ends with most of its types undecided; with it, the positive
verdicts (immutable, immutable with hidden content) appear.

Cycle breaking is deliberately conservative about the _strength_ of what it concludes: a type whose
deep immutability rests on a broken cycle is published at the hidden-content level rather than the full
level, because the unbroken evidence is not there.

A second kind of residue is not a cycle at all, but a verdict that _will never arrive_: an external, unannotated
type has no immutability value, any type holding a non-private field of such a type cannot conclude,
and — since "has a field of an undecided type" closes transitively — the undecidedness cascades through
the field graph.
Test code, which touches unannotated framework types most, made up the bulk of the cluster.
The breaking pass treats these the same way it treats blocked supertypes: a missing field or
abstract-method verdict is resolved pessimistically, and the type concludes at final-fields level —
field finality being the one thing the analysis has, at that point, already established on its own.
The published result is deliberately weak, honestly arrived at, and — unlike an absent verdict —
usable by every downstream consumer.

== Annotated APIs as analysis hints

The analyzer ships curated property sets for the JDK — `String` is deeply immutable, `Object` is
immutable with hidden content, the collection interfaces are mutable, the functional interfaces carry
their link summaries — under the name _analysis hints_.
They are loaded after parsing, resolved against the compiled-types universe of the run, and pre-seed the
property store so that source-code analysis starts from knowledge rather than pessimism.
The difference is not cosmetic: without the hints, every path through a JDK type bottoms out in
"undecided", and the immutability side of the analysis barely concludes anything positive; with them, the
proving-ground code bases settle into full immutability distributions.

== When code refuses to cooperate

A static analyzer that dies on the first pathological method is useless on real code.
Fault tolerance has three tiers:

* _method-level containment_: an exception while linking a method marks it _degraded_: it carries no links, counts as modifying, and its outputs are unspecified to
  the nullability pass — the element stays alive, pessimistically;
* _cycle protection with a tight ceiling_: run-away closures are cut off early and fall back to the method's
  shallow summary, at reduced precision;
* _guards at the boundaries_: unrepresentable link shapes are skipped at the point of production, and
  every skip is a logged, countable event rather than a silent loss.

[#after-the-fixpoint]
== After the fixpoint: the reachability passes

Two conclusions are deliberately _not_ computed inside the iteration: the propagation of modification along
call chains deeper than the summaries carry it, and nullability.
Both have the same shape — a seed, and a closure over the links — and both were tried inside the loop first.
There, a value written in an early pass froze the optimistic answer (unmodified, not null) before the
evidence against it had arrived, and the write-once discipline then kept it.
They run instead as _reachability passes_ over the converged link facts.

The modification pass is a _cutover_: it re-derives which methods,
parameters and fields are modified from primitive evidence and the converged links, downgrades the frozen
optimistic values it contradicts — the one place a verdict is allowed to get worse —
freezes the three modification properties, clears the immutability, independence and container verdicts
derived from them, and lets the loop re-derive and re-certify.
A chain deeper than one round reaches takes another, up to a fixed safety bound.

The nullability pass is the one-shot one: complete facts, after the cutover, every value
written once.
The chapter on <<nullability>> describes what it computes.
Mechanically:

* its _nodes_ are the fields, parameters, return values and locals of the analyzed code, plus a node per
  type argument and per array element of each;
* its _seeds_ are the null literals, the fields that can hold their default value, the arrays created empty,
  the library results declared nullable, the nullable contracts, and by default the parameters and fields
  that the code compares with `null`;
* its _edges_ are the direct links of each method's variable data, the argument links of each call site, and
  the override chains;
* its _guards_ are the per-statement facts of a forward walk over every method body — which variables are
  known not to be `null` where — and an edge is not taken where its source is guarded.

The pass runs in rounds.
A round trusts no analyzed method's return value; the next round treats every return value the previous one
found unreached as a non-null value at its call sites, and drops the edges from those sites.
Dropping edges only shrinks what `null` reaches, so the trusted set grows monotonically; a round also hands
the next the preconditions it found, so that an argument to one is known not to be `null` after the call.
The verdicts go into the same property store as everything else, from where the Java decorator, the Kotlin and
C# printers and the IDE read them.

What the pass needs from the iteration is that the link engine keeps the null markers in the method summaries and
records the argument links at every call.
Both change the content of the summaries, and are therefore off unless nullability is asked for.
