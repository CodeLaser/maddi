[[ownership]]
= Ownership

[IMPORTANT]
====
*Computed, behind a gate.* The verdicts of this chapter are computed by a separate pass that runs after the
analysis has converged.
It only adds verdicts: it never changes the modification, independence or immutability verdicts of the earlier
chapters, and nothing in the analysis reads its results back.
The pass is off by default; the environment variable `OWNERSHIP` switches it on, and `OWNERSHIP_WORLD=closed`
tells it that the analysed code is an application rather than a library (see <<ownership-transfer>>).
The design notes are in maddi-mod, `docs/roadmap/ownership.md`.
====

The previous chapters asked who can _modify_ an object.
Independence (<<linking-dependence>>) answers whether modifications can travel between two objects; it lets two
holders share immutable content, because nothing can travel through it.
This chapter asks a different question: who _holds_ an object?

The question matters as soon as Java code has to be translated into a language without a garbage collector.
In Rust, an object has one owner, and its lifetime is that of its owner; a value held in several places must be
wrapped in a shared, reference-counted handle.
A field whose object nobody else holds can be a plain field; a method whose result nobody else holds can return it
by value; a parameter the method does not keep can be borrowed.
The first consumer of the verdicts is the Java→Rust translation.

Ownership differs from independence in two ways.

* Immutable sharing counts. A field holding a `String` that its caller passed in is independent of that caller, as
modifications cannot travel through a `String`; but the object is shared, so the field does not own it.
* Ownership is a claim about the _absence_ of links: nobody else holds the object.
A missing or degraded summary of a method therefore always reads as "shared", never as "owned".

Three annotations express the verdicts: {fresh} on a method, {borrowed} on a parameter, {owned} on a field.

[#fresh-methods]
== Fresh methods

****
*Definition*: a method is *fresh*, marked {fresh}, when every object it returns was created during the call, or is
`null`, and nothing outside the call holds it when the method returns: the caller owns the result.
****

A method is fresh when every return path yields an object created in the method, the result of a call to another
fresh method, or `null`, and that object is not linked to the receiver, a parameter, a field or a static.

.Example {counter:example}, fresh and non-fresh methods
[source,java]
----
class Lines {
    private final List<String> lines = new ArrayList<>();

    @Fresh
    List<String> copy() {           // <1>
        return new ArrayList<>(lines);
    }

    @Fresh
    List<String> sorted() {         // <2>
        List<String> result = copy();
        Collections.sort(result);
        return result;
    }

    List<String> orEmpty(List<String> list) {   // <3>
        return list == null ? new ArrayList<>() : list;
    }

    List<String> registered() {     // <4>
        List<String> result = new ArrayList<>();
        registry.add(result);
        return result;
    }
}
----

<1> A new object, holding the elements of `lines`: the elements are shared, the list is not.
<2> The result of a fresh method, modified before it is returned: still fresh.
<3> One return path yields the parameter.
<4> The new object is also held by `registry`.

A lambda or a method reference is not a created object: the Java Language Specification allows every evaluation of
the same lambda to return the same instance (JLS 15.27.4, 15.13.3), so a method returning one is not fresh.
A method that calls itself starts out as not fresh, and stays so unless other evidence decides it.

On a method without a body, an abstract method or a library method in the annotated APIs, {fresh} is a contract
that every implementation must honour.
The JDK's annotated APIs carry a small first set: `Arrays.copyOf`, `Collection.toArray()`, `ArrayList.clone`,
`String.toCharArray` and `Map.entry` are fresh, for example.
`List.copyOf` is not: it may return its argument.
Neither is `Collections.emptyList`, which returns a shared instance.
An abstract method without a contract is fresh only when all its implementations are.

[#borrowed-parameters]
== Borrowed parameters

****
*Definition*: a parameter is *borrowed*, marked {borrowed}, when nothing that outlives the call holds the argument's
object when the method returns.
****

A borrowing method may read the object, modify it, and keep what it contains.

.Example {counter:example}, borrowed and kept parameters
[source,java]
----
class Lines {
    private final List<String> lines = new ArrayList<>();

    int countEmpty(@Borrowed List<String> list) {   // <1>
        int n = 0;
        for (String s : list) if (s.isEmpty()) n++;
        return n;
    }

    void addAll(@Borrowed Collection<String> c) {   // <2>
        lines.addAll(c);
    }

    void add(String line) {                         // <3>
        lines.add(line);
    }

    Runnable printer(List<String> list) {           // <4>
        return () -> list.forEach(System.out::println);
    }
}
----

<1> Read only.
<2> `addAll` copies the elements: `lines` holds the strings, not the collection.
<3> `lines` holds the object itself. It is a `String`, so `line` is independent, but not borrowed.
<4> The returned lambda captures the parameter.

The method keeps a parameter when a field of the receiver, a static, the return value, another parameter's content,
or a lambda or object that escapes, holds a link to the parameter's object itself.
A link to its hidden content does not count: that is the case of `addAll`.
Calling a method that keeps its argument keeps it too; a method that cannot be analysed fully (a degraded method) is
assumed to keep all its parameters.

On a parameter of a method without a body, {borrowed} is a contract, which every implementation must honour.

[#owned-fields]
== Owned fields

****
*Definition*: a field is *owned*, marked {owned}, when the object it holds can only be reached through the object
holding the field.
The owned object lives and dies with its owner.
****

The analyzer marks a field owned when four rules hold.

. *Arrives fresh.* Every value assigned to the field, in constructors, initializers and methods, is an object
created for it, the result of a fresh method, or `null`. A parameter qualifies only when it is transferred
(<<ownership-transfer>>).
. *Never leaves.* No link takes the field's object to a return value, a parameter, a static, a field of another
object, or an escaping lambda.
Passing it to a borrowed parameter is allowed, and so is returning it from a method whose result every caller only
uses (_lending_: Rust's `&self.f`).
. *Not accessible.* The field is private, or, in a closed world, no code outside its primary type mentions it.
. *No degraded referrer.* No method referring to the field has a degraded analysis.

.Example {counter:example}, owned and non-owned fields
[source,java]
----
public class Document {
    @Owned
    private final List<String> lines = new ArrayList<>();    // <1>

    @Owned
    private StringBuilder buffer;                              // <2>

    private final List<String> tags;                           // <3>

    private final Map<String, String> index = new HashMap<>(); // <4>

    public Document(List<String> tags) {
        this.tags = tags;
    }

    public void append(String s) {
        if (buffer == null) buffer = new StringBuilder();
        buffer.append(s);
        lines.add(s);
    }

    public Map<String, String> index() {
        return Collections.unmodifiableMap(index);
    }
}
----

<1> Created for the field, and it never leaves.
<2> Created lazily: every assignment is still a creation.
<3> The public constructor stores its parameter, which a caller may go on using.
<4> The unmodifiable view shares the object: a holder of the view sees every change to `index`.

A field that is not owned only because it shares an immutable object (a `String`, say, stored from a parameter) is
_shared immutable_: in Rust, a reference-counted value nobody modifies.
There is no annotation for it, as {immutable} on the field's type says it.
Static fields and fields of primitive type are not considered.

{owned} has one parameter, `elements`.
`@Owned(elements = true)` says that the elements of the field's collection, map or other generic object, its hidden
content, are owned too: each arrives created for it, or is handed over by every caller (<<ownership-transfer>>), and
none leaves.
In Rust, such a field is a vector of plain values rather than of shared handles.

The analyzer does not read {owned} as a contract: unlike {fresh} and {borrowed}, it concerns a field, which only the
code of its own type can judge.

[#ownership-transfer]
== Transfer

Rule 1 rejects a field assigned from a parameter: in general the caller may go on using the object.
When the analyzer can see every call site, it can check that they do not.

****
*Definition*: a parameter is *transferred* when every call site passes an object that is created on the spot, or is
held by a local that the caller does not use after the call; and the method keeps the parameter only in one field.
****

.Example {counter:example}, a parameter handed over by every caller
[source,java]
----
public class Parser {
    @Owned
    private final List<Token> tokens;            // <1>

    private Parser(List<Token> tokens) {
        this.tokens = tokens;
    }

    public static Parser of(String source) {
        List<Token> tokens = new ArrayList<>();
        tokens.add(new Token(source));            // <2>
        return new Parser(tokens);                // <3>
    }
}
----

<1> Owned: the private constructor's only caller hands its list over.
<2> Before the hand-over, the local is only the receiver of calls that keep nothing of it.
<3> The last use of `tokens`.

All call sites are known when the method is private or package-private, or when the world is closed
(`OWNERSHIP_WORLD=closed`): the analysed code is an application, and no code outside it calls its public methods.
The method must also not override anything, nothing may override it, and no method reference may name it.

{finalizer}, the subject of the next section, is a transfer of the receiver.

[#finalizers]
== Finalizers

[NOTE]
====
*Partially implemented.* {finalizer} is read as a contract, from source annotations and from the annotated APIs,
and its modification semantics (<<finalizer-exemption>>) are implemented and load-bearing.
When the ownership pass is switched on, it also checks the call sites of contracted finalizers for a use of the
receiver after the call, and computes {finalizer} on some methods (<<finalizer-transfer>>).
The three sequencing rules of <<finalizer-rules>> are not enforced as stated.
====

Up to now, we have focused on the distinction between the building phase of an object's life-cycle, and its
subsequent immutable phase.
We have ignored the destruction of objects: critically important for some applications, but often completely
ignored by Java programmers because of the silent background presence of the garbage collector.
The annotation {finalizer} marks that calling a certain method means that the object has reached the end of its
life-cycle:

****
Once a method marked {finalizer} has been called, no other methods may be subsequently applied.
****

Why is this useful?
The most obvious use-case for immutability is the meaning of the `build()` method in a builder: can you call it once,
or is the builder somehow incremental?
Secondly, consider "terminal" operations such as `findAny` or `collect` on a stream. They close the stream,
after which you are not allowed to use it anymore.

In the terms of this chapter, a finalizer is a _transfer of the receiver_: the caller hands the object over to the
call, and does not use it afterwards.

[#finalizer-exemption]
=== Why the modification exemption matters

A finalizer marks the end of an object's life-cycle: after the call, the object may not be used again.
Whatever the finalizer does to the dying object is therefore invisible to the rest of the program — there
is no "after" in which the change could be observed. The analyzer exploits this: *a call to a
{finalizer} method never marks its receiver as modified*, whatever the method's own {nm}/{modified}
status.

This is not a corner case; it is what keeps stream-based code analyzable at all. The annotated APIs mark
the stream operations — `filter`, `map`, `flatMap`, `collect`, and their relatives — as {finalizer}:
each consumes the stream it is called on (using the receiver again afterwards is illegal), and none of
them carries a {nm} contract. Without the exemption, every one of those calls would conservatively count
as a modification of the receiver chain, and since a chain such as `this.elements.stream().map(...)`
roots in a field, the false modification would climb to the field and to `this` — making essentially
every method containing a stream pipeline {modified}, and sinking the immutability of its type. With the
exemption, the pipeline is silent about its receivers, and only genuine evidence (the lambda's captures,
the collector's target) determines the verdict.

The same reasoning must be applied by *every* component that re-derives modification: when the
modification-reachability pass (the post-convergence single writer) judges a call to a method outside
the analysis scope, it mirrors the engine's guard exactly — a boundary callee that is a finalizer
contributes no receiver-modification evidence, no matter that its conservative no-information default
would otherwise read as "modifying". A mismatch here is not benign: it silently poisons whole call
chains with false modification, in code as central as the printing of a parameterized type.

[#finalizer-rules]
=== Sequencing rules

How can the analyzer enforce the sequence of method calling on an object?
The simplest way is by some severe restrictions:

****
The following need to be true at all times when using types with finalizer methods:

. Any field of a type with finalizers must be effectively final (marked with {final}).
. A finalizer method can only be called on a field inside a method which is marked as a finalizer as well.
. A finalizer method can never be called on a parameter or any variable linked to it, with linking as defined throughout this document (see <<linking-dependence>>).
****

These restrictions help you control the life-cycle of objects with a {finalizer}, by not letting them out of sight.
Each of them is an ownership rule:

[cols="1,1"]
|===
|Rule |In ownership terms

|no method may be called after the finalizer
|the receiver is not used after the call: a transfer (<<ownership-transfer>>), with the receiver as the argument
|1. a type with finalizers has effectively final fields
|the owner cannot be swapped out
|2. a finalizer is called on a field only inside a finalizer
|an owner consumes what it owns only while it is itself consumed (in Rust, moving out of a field needs `self` by value)
|3. never on a parameter, or anything linked to it
|a borrowed object cannot be consumed
|===

The eventually immutable types of the next chapter use finalizers to keep an object in its _before_ state while it
is held by a field (<<finalizers-before-mark>>).

[#finalizer-transfer]
=== Computing and checking finalizers

A finalizer may hand over an owned field of its own object (`return new Result(this.lines)` in a `build()`
method), and the field remains owned: after the call, its owner is dead.
When the ownership pass is on, the analyzer computes {finalizer} on a method that _needs_ to be one, because it
hands over an owned field of its own type, when it is also _permitted_ to be one, because every call site hands over
its receiver: a temporary (a construction, a fresh method's result, a chain of {fluent} calls on one), or a local that
is not used after the call.
Call-site evidence alone would be vacuous: any method called once, on a temporary, would qualify.

For a contracted finalizer, the same test on every call site finds the uses of the receiver after the call, for
example a stream used again after `map`.
They are reported as warnings: the modification exemption above relies on them not happening.

== Ownership and modification

Ownership is a stronger form of independence for one field, parameter or result: an owned field is independent,
since no other holder exists through which a modification could travel; and a borrowed parameter is independent,
since nothing retains it.
The converse does not hold, because independence allows immutable sharing.

The examples of this chapter are pinned by the test `TestBook055Ownership` in maddi-mod.
The verdicts have also been checked against instrumented test runs, which record every place that holds a claimed owned
object, and every holder of a borrowed argument after the call.
The contradictions those runs found were holes in the pass, and are fixed.
